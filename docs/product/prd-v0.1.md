# Amoji 首版产品规格

版本：0.1。日期：2026-09-05。状态：产品方向及范围已由用户确认；流程细化、技术默认值和验收方法为本次规格设计。

## 1. 产品定位

Amoji 是一套独立、开放的 AI 原生表情体系，让人与 AI 共享表达：人看到图片或动图，AI 直接读取表情携带的文本语义。

人与 AI 协作中的情感表达是一项基础能力，不应以模型是否支持视觉、是否愿意承担重复识图成本为前提。用户是否使用、使用什么风格和多高频率，仍由用户决定。

本项目不以兼容传统 IM 表情协议为目标。外部图片可以成为创作材料；经语义定义与确认后，它们才成为 Amoji 表情。

“低成本”指避免每次收发表情都调用视觉模型或专用情感模型，不意味着零文本 Token、零工具调用或所有模型表现完全一致。

## 2. 首版目标

- **P01 双向表达**：用户能向 AI 发表情；AI 能选择表情并让用户看到视觉内容。
- **P02 文本语义路径**：正常收发、查找和历史回放无需模型识图。
- **P03 固定版本语义**：发送时引用已确认版本，不提供本次发送语义覆盖。
- **P04 用户创作**：文字意图、上传素材、语义建议、编辑和确认形成闭环。
- **P05 导入导出**：区分原始素材与完整 Amoji 包，支持本地迁移。
- **P06 个人编辑与历史稳定**：编辑产生新版本或个人副本，旧消息不变。
- **P07 AI 自主使用且可控**：按语境表达，提供风格、频率及暂停控制。
- **P08 本地共享**：无需 Amoji 账号，同设备三端共享表情库及个人设置。
- **P09 多宿主接入**：实现 dsh、Codex、Claude Code 适配，展示入口可不同；本期以 Codex 验证完整接入，其他宿主在验证工具不可用时可先实现并标记未验证。
- **P10 开箱可用**：内置约 20–30 个视觉与语义完整的基础表情。
- **P11 开放与用户所有权**：公开数据格式，开源核心与三端插件，个人表情默认不公开。

## 3. 核心用户场景

| 场景 | 用户行为 | 预期结果 |
|---|---|---|
| 轻松表达感谢 | 选择“谢谢啦”，可以只发送表情 | 人看到视觉；AI 得到固定语义并自然回应 |
| 一起完成阶段任务 | AI 自主选择适当的庆祝表情 | 用户看到表情；无需先给每次表达授权 |
| 表达无奈 | 用户发送“无奈自嘲”，另附普通文字解释事情 | 表情定义不变，文字作为正常对话上下文 |
| 建立个人表达习惯 | 用户修改内置表情的语气或含义 | 形成个人副本，之后使用自己的定义 |
| 创作新表情 | 用户描述想表达什么并上传图片 | 系统仅根据文字建议语义，用户检查图文并确认 |
| 更换客户端 | 从 dsh 切到 Codex 或 Claude Code | 同一表情版本与个人设置仍可使用 |

“理解语义”不等于根据表情推断用户真实心理状态；表情也不替代宿主对文件删除、发布等操作的授权。它参与正常表达。

## 4. 交互流程

### 4.1 用户发送

1. 打开内嵌选择器或与当前会话关联的配套面板。
2. 浏览、搜索表情；选择时能看到视觉内容和简短含义。
3. 点击发送；可单发表情，也可搭配普通文字。
4. 系统固定本次引用的表情版本，记录消息并投递该版本的语义。
5. 当前会话或关联面板显示对应视觉，并区分待投递、已投递和失败。

正常流程不要求用户填写结构化字段、选择版本号或解释“这一次”的表情含义。复制引用到宿主输入框可以作为诊断或临时兼容方案，不能据此直接宣称已达到完整选择发送体验。

### 4.2 AI 发送

1. AI 根据上下文和用户设置决定是否使用表情。
2. 按文字查询表情库，取得少量候选的语义和准确版本引用。
3. 选中候选并请求发送；运行时验证可用性、频率和当前会话目标。
4. 视觉展示给用户，模型仅接收文本语义和投递结果。

没有合适表情时正常用文字回复，不创造不存在的 ID，不把另一张图偷偷赋予临时含义。可选的语气说明是表情定义的一部分，不是发送参数。

### 4.3 创建与语义建议

- 用户先提供“想表达什么”和视觉素材；系统可建议名称、含义、语气、适用语境、替代文本和检索标签。
- 建议仅依赖文字，不要求视觉模型；用户预览视觉并确认图文匹配。
- 建议不可用时允许用户手工完成，保存草稿不等于已可发送。
- 首版不内置 AI 绘图，不强制配置新的模型供应商或注册 Amoji 账号。
- 人工确认形成可用版本；系统之后不会在后台自动重写已确认语义。

### 4.4 导入与导出

| 输入 | 处理 |
|---|---|
| 原始图片或动图 | 进入创作流程；补齐并确认语义后才可使用 |
| 完整 Amoji 包 | 校验格式、文件、版本一致性和素材完整性后导入；不强制逐个重做语义确认 |
| 不完整、损坏或不支持的包 | 明确报告具体原因，不留下半导入的可用表情 |

导出由用户主动选择范围，携带所选版本及其素材。默认不包含会话、使用记录、个人设置或机器路径。个人设置使用独立备份路径，避免分享表情时附带私人偏好。

### 4.5 编辑与历史

- 编辑自己创建的表情：保留旧版本，保存新的不可变版本，更新自己的默认使用版本。
- 编辑内置或外部导入表情：先创建个人副本，后续编辑作用于该副本。
- 发送时锁定版本；其他窗口的同时编辑不得替换已选中的版本。
- 从常用库移除采用归档；历史消息仍可找到原语义与视觉素材。
- 库版本更新不重写宿主历史，也不更新既有消息的含义。

### 4.6 风格、频率和动画

风格与频率是个人设置，同机三端共享。工程初始方案为“克制 / 适中 / 活跃”和“暂停 AI 自发表情”，默认克制；风格用可编辑的简短偏好描述，不建立复杂人格系统。

暂停只影响 AI 主动表达，不阻止用户自己发表情或 AI 理解用户表情。默认避免连续重复；准确冷却规则见技术设计，可依据真实体验调整。

支持静态图片和短循环动图。用户能暂停动画；减少动态效果时显示静态封面。显示失败可暂时使用替代文本，但仅有文字的正常路径不满足双向视觉目标。

## 5. 基础表情库

目标约 20–30 个；首轮按 24 个设计内容清单，最终图像与名称在内容制作时确定。本清单是创作方向，不是已制作的资产。

| 类别 | 表达示例 | 建议数量 |
|---|---|---:|
| 喜悦与庆祝 | 开心、完成啦、击掌、期待 | 4 |
| 感谢与认可 | 谢谢、佩服、点赞、收到心意 | 4 |
| 鼓励与陪伴 | 加油、抱抱、慢慢来、辛苦了 | 4 |
| 疑惑与思考 | 疑惑、思考中、恍然大悟、请展开 | 4 |
| 无奈与调侃 | 无奈自嘲、尴尬、轻松认输、调皮 | 4 |
| 日常关系表达 | 打招呼、告别、歉意、放松一下 | 4 |

语义用自然语言表达，不强制归约成“正面/负面”或单一情绪数值。内置表情需要视觉与语义共同评审，素材具备可随项目分发的明确许可。

开发阶段的样本与基础库图片使用 Codex 的 imagegen 技能制作，最终素材保存到项目并记录生成提示与来源。动图需要另行完成封装、封面与播放验证，静态图片生成成功不等于动图完成。这是开发素材的生产方式，不增加首版产品内置绘图入口，也不改变日常收发无需识图的要求。

## 6. 三端体验与支持声明

首版代码范围覆盖三个宿主。本期以 Codex 为真实完整接入的验证基准，优先使用 Codex Desktop；dsh 或 Claude Code 的验证工具不可用时，允许先完成适配实现并跳过对应真机验证，不阻塞 Codex 主线交付。

实现状态与验证状态必须分别记录。其他宿主应完成实际适配逻辑及可执行的构建、类型与合同检查，不以空壳或固定成功返回算作实现。缺少运行环境标为“已实现、宿主未验证”，记录缺失工具和跳过用例；实际运行失败仍是失败，不能改写为跳过。工具可用时继续验证。每个宣称“已验证支持”的具体客户端仍必须具备真实双向证据。

dsh Web、Codex Desktop、Codex CLI、Claude Code CLI、IDE 分别记录，不从同品牌或 Codex 基准的结果推断其他形态已通过。Codex 自身的完整接入与纯文本请求证据不属于可跳过范围。

允许的产品形态：

- 宿主具备合适扩展点时，选择与视觉显示内嵌在会话中。
- 其他形态使用配套面板，但必须明确关联当前会话并完成发送和接收。
- “打开图库”“复制文本”“模型能读到工具结果”可证明局部能力，不能单独证明整体接入。

宿主缺少必要公开能力时，如实标为实验或不支持；不得更换成自建客户端后仍称已支持官方客户端。具体目标形态与版本由技术验证表收敛。

## 7. 首版不包含

- 传统 IM 协议适配、已有表情生态的自动语义补全。
- 每次发送修改语义、自动替用户重定义表情。
- 内置 AI 绘图、自动识图作为必要步骤。
- Amoji 账号、云端自动同步、公共市场和自动分享。
- 声音、长视频、交互式角色、3D 形象。
- 通过训练专用模型或逐次情绪分类器才能运行的方案。

## 8. 已确认决策追踪

| 访谈 | 最终决定 |
|---|---|
| 产品原则 / Q1 | 情感表达是基础能力，不能受视觉模型和重复识图成本限制 |
| Q2 | 首版包含用户到 AI、AI 到用户两个方向 |
| Q3 | 独立表情体系，不以兼容已有 IM 表情协议为目标 |
| Q4 | 系统建议与用户定义结合，用户可修改语义 |
| Q5 | 原始素材先创作确认；完整 Amoji 包可校验后直接导入 |
| Q6 | 个人新版本、未来生效、历史保留、不影响他人 |
| Q7 | AI 按语境自主使用，用户控制风格和频率 |
| Q8 | 文字意图与视觉素材创建；首版不内置绘图 |
| Q9 | 本地优先、无需账号、同机共享、包迁移 |
| Q10 | 允许不同展示入口，必须保持双向视觉表达 |
| Q11 最终修正 | **不允许单次发送动态修改语义** |
| Q12 | 静态图片与短循环动图 |
| Q13 | 内置约 20–30 个基础表情 |
| Q14 | 开放格式、开源核心和三端插件，个人库默认私有 |
| 整体确认 | 用户确认汇总，进入 PRD、数据协议和三端技术设计 |
| 本期验证策略修订 | Codex 为完整接入基准；其他宿主在验证工具不可用时先实现、跳过真机验证并明确标注，不阻塞主线 |
| 素材生产方式 | 开发阶段使用 Codex imagegen 技能生成表情图片；产品首版仍不内置绘图功能 |

## 9. 完成判据

实现须按[验收矩阵](../planning/acceptance-v0.1.md)完成 Codex 的真实视觉呈现、文本语义输入、无必要图像模型输入、创作与迁移、历史及多会话验证。其他两端须完成适配实现与可执行检查；仅因验证工具不可用而跳过的宿主测试明确记账。三端共享合同保持一致，本期不要求用缺失的宿主环境证明真机共享已通过。

文档完成、Schema 合法、插件安装成功或构建成功，均不能单独作为产品完成证明。
