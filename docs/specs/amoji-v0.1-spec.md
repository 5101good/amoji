# Amoji v0.1：面向 dsh、Codex 与 Claude Code 的 AI 原生表情体系

日期：2026-09-05。类型：首版功能 Spec。产品共识已确认；用户指定 Codex 为完整接入验证基准；Issue Tracker 待配置。发布时使用标签 `ready-for-agent`，当前尚未创建或标记任何 Issue。

## Problem Statement（问题陈述）

人与 AI 协作时，需要通过表情表达感谢、庆祝、鼓励、安慰、疑惑、无奈和调侃。人类熟悉的视觉表达不应因为 AI 使用纯文本模型，或因为重复识图带来的成本与延迟，而无法参与对话。

一张普通图片并不天然为纯文本 AI 提供准确语义。如果每次都让视觉模型识别，会增加使用成本，也可能将用户原本的表达解释成其他含义。用户希望人和 AI 共享一种可直接使用的表情对象：人看到视觉内容，AI 获得用户认可的文本语义。

目前 Amoji 已形成产品规格、领域词汇、数据协议、Schema、技术设计及验收计划，但尚无运行实现。三种宿主对界面扩展和会话接入的能力不同，必须实际证明用户发送和 AI 回复都能抵达正确会话，并显示对应视觉，才能宣称支持该宿主。

## Solution（解决方案）

建立独立、开放的 Amoji 表情体系。每个表情版本同时携带视觉素材和已确认的表情语义；同一条表情消息的人类展示与模型输入由该版本派生。

用户能浏览、选择和发送静态图片或短循环动图，AI 通过文本语义理解，也能按语境自主选择表情回应。用户可调整 AI 的表达风格、频率或暂停主动表达。正常使用无需视觉模型、专用情感模型或 Amoji 账号。

用户通过文字意图和视觉素材创建表情，系统提供语义建议，用户修改并确认。用户可导入完整表情包，或将原始素材经创作确认变成表情。编辑生成新版本或个人副本，保留历史消息的视觉和语义。

采用同设备共享的本地表情库及核心能力，通过三个宿主适配器接入 dsh、Codex 和 Claude Code。具备适当能力的客户端采用内嵌界面，其他客户端可使用明确关联当前会话的配套面板。基础库提供约 20–30 个可直接使用的表情。

交付分为两个阶段：

1. 先用两个静态表情与一个短循环动图在 Codex 验证当前会话绑定、双向交互、纯文本模型输入、历史回放及多会话隔离，优先采用 Codex Desktop。开发素材使用 Codex imagegen 技能生成，动图另行封装并验证。
2. Codex 接入路线成立后，完善共享表情库、创建与编辑、导入导出、个人设置、基础内容及三个宿主适配器。dsh、Claude Code 验证工具不可用时，完成实际适配实现与可执行检查，允许跳过对应真机验证并明确标记，不阻塞 Codex 的完整交付。

第一阶段完成只是接入验证完成；不能代替完整首版交付。

## User Stories（用户故事）

1. 作为人与 AI 协作的用户，我希望表情成为日常表达方式，以便自然地表达文字之外的语气和感受。
2. 作为使用纯文本模型的用户，我希望 AI 能直接读取表情语义，以便不因模型缺少视觉能力而失去表情交互。
3. 作为关注使用成本的用户，我希望每次收发表情都无需重新识图，以便减少不必要的费用和等待。
4. 作为用户，我希望使用独立的 Amoji 表情体系，以便表情定义不依赖某个传统 IM 软件。
5. 作为新用户，我希望安装后即可使用约 20–30 个基础表情，以便无需先制作自己的表情库。
6. 作为新用户，我希望基础库覆盖感谢、庆祝、鼓励、安慰、疑惑、无奈和调侃，以便表达常见的互动语气。
7. 作为用户，我希望能够浏览视觉表情，以便通过看图选择符合当前表达的内容。
8. 作为用户，我希望按自然语言、名称或标签搜索表情，以便快速找到合适的表达。
9. 作为用户，我希望选择时能查看表情的固定含义，以便知道 AI 将收到什么语义。
10. 作为用户，我希望可以只发送一张表情，以便保持日常聊天的轻便体验。
11. 作为用户，我希望表情可以搭配普通文字发送，以便补充上下文而不修改表情定义。
12. 作为用户，我希望发送时无需填写本次语义，以便像日常使用表情一样直接选择和发送。
13. 作为用户，我希望发送时使用自己选中的确定版本，以便另一窗口的编辑不会悄悄改变本次表达。
14. 作为用户，我希望看到待投递、已投递、失败或未知的真实状态，以便知道表情是否进入目标会话。
15. 作为用户，我希望失败时保留我的选择并给出可理解的原因，以便能够处理问题而无需重新创作表情。
16. 作为用户，我希望缺失或错误的表情引用被明确指出，以便系统不会用同名的新表情替代我的选择。
17. 作为用户，我希望 AI 能结合普通对话上下文理解固定语义，以便无需在每次发送时重新解释表情。
18. 作为用户，我希望 AI 能按语境自主选择表情，以便互动中自然出现回应、庆祝和陪伴。
19. 作为用户，我希望 AI 依据已确认的语义选择真实存在的表情，以便不会收到凭空生成的引用或错误图片。
20. 作为用户，我希望没有合适表情时 AI 可以正常用文字回应，以便表达不会被不合适的表情打断。
21. 作为用户，我希望 AI 发送的图片与其选择的语义来自同一版本，以便视觉和含义一致。
22. 作为用户，我希望调整 AI 使用表情的风格，以便它符合我的交流习惯。
23. 作为用户，我希望调整 AI 使用表情的频率，以便表达不会变成刷屏。
24. 作为用户，我希望可以暂停 AI 主动发表情，以便在需要时保持简洁的交流。
25. 作为用户，我希望暂停 AI 主动表达后仍能自己发表情并被理解，以便保留自己的表达自由。
26. 作为用户，我希望工具重试不会重复发送同一表情消息，以便网络或宿主故障不造成重复表达。
27. 作为用户，我希望能使用静态图片和短循环动图，以便保留动作与节奏带来的表现力。
28. 作为用户，我希望能够暂停动画并查看静态封面，以便按自己的阅读偏好控制动态效果。
29. 作为需要替代呈现的用户，我希望表情具备准确的替代文本，以便视觉无法加载或使用无障碍方式时仍能理解表达。
30. 作为创作者，我希望输入文字意图并上传视觉素材，以便建立自己的表情。
31. 作为创作者，我希望系统根据文字意图建议语义，以便降低定义表情的工作量。
32. 作为创作者，我希望修改建议中的含义、语气、语境和替代文本，以便由我决定表情表达什么。
33. 作为创作者，我希望在确认前预览图文，以便检查视觉与语义是否匹配。
34. 作为创作者，我希望未确认的草稿不会被 AI 检索或发送，以便避免使用尚未完成的定义。
35. 作为创作者，我希望语义建议不可用时仍可手工完成表情，以便创作不被模型服务可用性阻断。
36. 作为用户，我希望导入原始图片后进入语义定义流程，以便它成为可供 AI 理解的完整表情。
37. 作为用户，我希望完整且合法的 Amoji 包可以直接导入，以便不必重新确认包内每一张表情。
38. 作为用户，我希望损坏、不支持或不完整的包给出明确错误，以便不会得到半导入的表情库。
39. 作为用户，我希望重复导入相同定义不会创建重复表情，以便保持表情库整洁。
40. 作为用户，我希望相同版本标识但内容不同的包被拒绝覆盖，以便已有表情定义保持稳定。
41. 作为用户，我希望导出所选表情及其完整素材，以便分享或迁移时不依赖原机器的文件位置。
42. 作为用户，我希望导出包默认不包含会话、个人设置和使用记录，以便分享表情时保留私人信息。
43. 作为用户，我希望在新的本地数据环境中导入表情包后恢复相同语义与视觉，以便迁移后继续使用。
44. 作为创作者，我希望编辑自己表情时形成新版本，以便改进定义并保留过去的表达。
45. 作为用户，我希望编辑内置或外部表情时形成个人副本，以便不改变原作者或其他人的定义。
46. 作为用户，我希望历史消息保留发送时的版本，以便后来修改表情不会改变以前对话的意思。
47. 作为用户，我希望归档表情后旧消息仍能展示，以便整理表情库不会破坏历史。
48. 作为同时使用多个客户端的用户，我希望并发编辑出现冲突时得到提示，以便不会静默丢失自己的修改。
49. 作为用户，我希望表情库和设置保存在本机且无需 Amoji 账号，以便自主掌握自己的数据。
50. 作为多宿主用户，我希望同设备上的三个客户端共享表情库和个人设置，以便不用分别维护三套内容。
51. 作为用户，我希望插件升级或移除一个客户端的插件时保留共享库，以便其他客户端和历史仍可使用。
52. 作为 dsh 用户，我希望在真实 dsh 会话中完成表情收发，以便保留原有协作环境。
53. 作为 Codex 用户，我希望通过可分发的插件路径完成表情收发，以便无需依赖当前开发会话独有的内部工具。
54. 作为 Claude Code 用户，我希望在明确支持的常规环境中使用表情，以便知道安装和运行所需的真实条件。
55. 作为需要配套面板的用户，我希望面板显示其关联的宿主与会话，以便不会把表情发到错误位置。
56. 作为用户，我希望在面板选中的表情直接进入已关联会话，AI 选择的表情自动显示，以便形成完整双向交互。
57. 作为同时打开多个会话的用户，我希望切换、暂停与重连都不会串话，以便不同协作上下文保持独立。
58. 作为用户，我希望恢复会话时仍看到原版本的静态图片或动图，以便历史体验保持一致。
59. 作为用户，我希望知道某个客户端的支持状态与限制，以便区分正式支持、实验路径和不支持的能力。
60. 作为用户，我希望表情表达不被当作其他操作的授权，以便自然交流不会改变宿主已有的操作边界。
61. 作为用户，我希望个人表情不会自动公开，以便由自己决定是否分享。
62. 作为开发者，我希望表情格式公开且核心实现和三个插件开源，以便检查、扩展或接入其他客户端。
63. 作为维护者，我希望先用少量样本取得 Codex 完整接入证据，并在其他宿主验证工具不可用时先完成实现且明确标注，以便推进本期开发而不虚报支持能力。
64. 作为维护者，我希望每个支持声明都对应可复现的视觉、模型请求和会话记录证据，以便准确判断交付是否完成。

## Implementation Decisions（实现决策）

1. **产品边界**：实现独立表情体系，保持用户已确认的双向表达、本地优先与开放格式。使用表情与否由用户决定，不强制增加每次发送的操作步骤。
2. **统一领域模型**：核心对象为表情、表情版本、表情语义、表情消息、个人副本、表情库、表情包和宿主适配器；不把单张图片、插件包或模型心理推断混称为表情。
3. **固定语义**：每个已确认版本只有一份语义。表情消息和发送接口没有单次语义覆盖；用户补充的文字保留为普通对话内容。
4. **版本与身份**：表情与版本分别使用稳定标识。发送锁定精确引用；不以名称或“最新版本”解析历史。相同版本标识的内容不可变，冲突拒绝覆盖。
5. **双投影**：消息的人类视觉投影与模型文本投影从同一版本构造。语义进入模型可见文本；视觉通过宿主渲染器或配套面板读取本地素材。语义不得只放在宿主隐藏元数据中。
6. **持久历史**：消息保存确定版本的完整快照并保留素材引用。回放不跟随库当前版本；图片丢失时显示替代文本与异常，不换成其他图片或调用模型识图补救。
7. **共享核心**：建设资产与草稿管理、不可变版本、素材存储、检索、设置和消息投递模块，三个适配器共同连接。界面与宿主细节不进入资产定义。
8. **工程栈方案**：已有设计提出 TypeScript、本地单用户服务、SQLite 元数据和按摘要保存的素材。它们是当前工程方案，协议不绑定语言、数据库或模型供应商；不把尚未实现的栈写成既成代码。
9. **本地归属**：库独立于宿主插件安装缓存。同设备只维护一份用户库；并发更新检查修改序号，插件升级或单端卸载不自动删除共享数据。
10. **日常工具接口**：提供 `amoji_search`、`amoji_resolve`、`amoji_emit`。检索返回少量完整语义候选和准确引用；解析使用精确版本；发送只接受服务生成的选择凭据。
11. **工具输入限制**：发送不接受模型重新填写语义、图片地址、任意消息快照或目标会话。核心从凭据恢复选择并校验当前策略、版本可用性和会话绑定。
12. **检索与成本**：初始采用本地文字检索，无需向量服务或逐次情绪分类器。不把整库注入每轮提示，不重复复制完整语义到多个模型可见字段。报告真实文本与工具成本，不声称零成本。
13. **表达策略**：AI 按语境自主表达，用户可调整风格、频率及暂停。初始采用克制默认值、单回合数量限制和重复冷却；强制回合策略依赖可信宿主回合标识，不接受模型自报回合。
14. **创建合同**：语义建议器只根据文字意图形成草稿；用户检查视觉并确认后才生成可发送版本。无建议器时保留完整手工流程，不要求配置新的视觉模型。
15. **个人修订**：编辑本人创建的表情保留身份并生成新版本；编辑内置或外部表情生成个人副本，保留来源关系。导入不能伪造本机作者归属。
16. **素材合同**：支持静态 PNG、JPEG、WebP 以及 GIF、animated WebP 动图；动图具备时长与静态封面。校验摘要、实际格式、尺寸和解码预算，不接受可执行视觉容器。
17. **协议与包合同**：沿用已有 v0.1 协议和 Schema；完整包包含清单、确定版本及所需素材。拒绝不支持的协议、冲突版本、缺失素材和不合法默认引用；导入原子提交。
18. **分享边界**：导出只携带用户选择的资产和素材，排除消息、绑定、绝对路径、个人设置与使用记录。导入旧包不自动切换用户已有个人版本。
19. **会话绑定**：每条消息关联可信的宿主实例与真实会话。工作目录、最近窗口或一个 MCP 进程本身均不能未经验证充当会话身份；切换窗口不改变待发目标。
20. **投递合同**：本地消息、待投递记录和去重键一同保存；提交宿主后分别记录宿主确认和人类显示。已提交不等于已展示，已展示不等于人已阅读或 AI 已理解。
21. **重试合同**：同一次发送凭据或请求标识重复执行时返回原消息，不新建重复表达。宿主侧结果无法确认时保留未知状态，不盲目重发或承诺跨系统严格一次投递。
22. **dsh 适配**：实现原生 Host/Client 插件、可回放的会话输入、工具输出投影与客户端视觉渲染，不能仅实现后端展示函数。执行可用的构建和合同检查；宿主验证工具不可用时记录跳过，保留真机补验步骤。
23. **Codex 适配**：验证可分发的 Skill/MCP 插件路径、稳定绑定以及 Desktop 视觉呈现。当前会话能显示本地图片是候选依据，不证明第三方插件与所有客户端均已支持。
24. **Claude Code 适配**：实现常规插件工具路径与配套面板，执行可用的构建和合同检查；验证工具不可用时允许跳过宿主实测并记录。预览通道可作满足条件环境的增强路线，不把开发允许名单绕过当作所有用户默认依赖。
25. **支持矩阵**：Codex 为本期完整接入基准，其他两端分别记录实现、构建、合同测试和宿主实测状态。环境缺失导致的跳过不代表通过；已运行失败的测试仍记失败。替换为自建客户端或仅复制文本引用，不能计为基准完整接入。
26. **接入原型边界**：第一阶段仅需三个受控样本与必要接口和记录；共享核心只依赖 Codex 的肯定接入证据。其他宿主缺少验证工具时继续实现，不重新阻塞核心；Codex 基准不允许因工具缺失而跳过完整验证。
27. **基础内容**：使用 Codex imagegen 技能制作样本与约 20–30 个基础表情，记录提示与来源并保存项目素材；动图另行封装与播放验证。图文一致性和素材分发许可共同评审，不把占位元数据当作已制作图片。这是开发阶段素材生产方式，不是新增产品绘图入口。
28. **公开发布**：公开协议，开源核心与三端插件，个人库默认私有。实际许可证、素材许可与分发信息在公开发布前落实；本 Spec 不代替这些工作。

## Testing Decisions（测试决策）

### 测试边界

采用一个主要产品测试边界：**真实 Codex 会话中，用户或 AI 发起一次表情表达，最终得到可核对的会话文本与视觉结果。** 三端保持同一行为合同；其他两端在验证工具可用时替换宿主驱动实测，不可用时记录跳过。

输入从用户可用的选择器/面板或宿主公开工具入口发起；观察用户实际可见结果、宿主持久记录及模型实际出站请求。图像渲染与请求捕获是这一产品边界的不同观察点，不拆成互不相通的“看图测试”和“语义测试”。

用户已指定以 Codex 验证完整接入，并允许其他宿主在验证工具不可用时先实现、后补验。Schema、包格式和适配器公共接口使用辅助合同测试；不以私有函数、数据库表结构、React 内部状态或内部调用次数作为通过条件。

### 好测试的标准与现有基础

1. 测试验证外部行为和约定，而非复述实现。一个内部重构只要保留行为，不应导致整套验收重写。
2. 核心资产、消息投递与 Codex 适配器通过上述产品路径共同验证；创建、修改和导入从公开用户操作或公共服务合同进入。其他适配器执行可用检查，宿主工具缺失时不要求不存在的真机证据，也不能只交空壳。
3. 对纯文本能力，同时观察适配器数据和宿主实际出站请求；仅证明工具返回字符串不够。首次收发、工具回传、后续回合、上下文恢复和重开历史都需检查。
4. 对模型理解使用允许多个合理候选的语境场景，评价其是否符合固定含义及普通上下文，不机械要求唯一 ID 或只看模型复述标签。
5. 故障测试模拟失联、超时、素材损坏、重复请求和并发编辑，在公开边界检查可见状态、历史与目标会话是否正确。
6. 当前项目没有应用代码或可复用的运行测试入口，也没有已完成的三端原型；不能虚构既有测试框架或借用其他项目的测试结论。
7. 已有基础是 20 项产品验收场景、6 个接入门槛和 v0.1 Schema 的 37 项结构断言。结构验证包含 8 个正例与 29 个反例，不代表真实素材、模型或客户端测试已通过。
8. 现有 Schema 自检曾发现默认时间格式校验实现缺失；后续验证器必须实际启用日期格式检查，不能仅声明格式字段。

### 必须通过的行为场景

下表是 Codex 本期必须完成的完整行为基准。跨宿主项在 Codex 多会话/多连接及共享服务合同上验证；dsh、Claude Code 的工具不可用时单列跳过的真机用例及原因，不虚报三端运行通过。实际失败与环境跳过分别处理。

| 编号 | 行为 | 判据 |
|---|---|---|
| T01 | 用户单发表情 | 当前会话收到固定语义，人类端显示对应视觉，AI 可自然回应 |
| T02 | AI 自主表达 | 仅按文本候选选择真实版本，用户看到匹配图片 |
| T03 | 纯文本路径 | 实际模型请求在首次、续聊与回放中不因 Amoji 包含图像输入 |
| T04 | 固定语义 | 发送时没有语义编辑入口，覆盖字段被拒绝，配文仍为普通文字 |
| T05 | 创建与建议 | 草稿可编辑，用户确认前不可发送，确认后图文与保存版本一致 |
| T06 | 手工创建 | 建议器失效时仍能完成合法表情 |
| T07 | 原始素材导入 | 缺少已确认语义的素材不能直接成为可发表情 |
| T08 | 完整包与冲突 | 合法包直接导入，重复幂等，损坏或同 ID 异内容原子失败 |
| T09 | 跨本地环境迁移 | 新数据环境中语义与素材摘要一致，无原机器路径依赖 |
| T10 | 编辑与回放 | 发送旧版、编辑新版、重开会话后仍显示旧版视觉和语义 |
| T11 | 个人副本 | 编辑内置或外部表情不改变原定义及其他引用 |
| T12 | 风格与暂停 | 用户设置影响 AI 新发表情，暂停后用户表达仍能被理解 |
| T13 | 幂等与频率 | 同一请求重试不重复显示，频率规则不阻断用户手动表达 |
| T14 | 同机共享与更新 | 三端看到同一版本与设置，升级或单端移除不破坏共享库 |
| T15 | 多会话与重连 | 两个会话同时运行、切换和恢复时均不串话 |
| T16 | 配套面板闭环 | 选择直达明确绑定的会话，AI 表情自动显示，单独打开图库不算通过 |
| T17 | 基础库完整性 | 约 20–30 个可用表情包含静态与动图，语义与视觉共同评审 |
| T18 | 导出与私有数据 | 包不携带会话、路径、设置或使用记录，个人库不自动发布 |
| T19 | 动图与替代呈现 | 动图播放、暂停、封面、历史恢复可用，缺图时不替换语义 |
| T20 | 投递故障与并发 | 提交前后断连准确标记失败或未知，重试不盲目重复，并发编辑不静默覆盖 |

Codex 必须验证实际出站请求只依赖文本；若可配置纯文本模型，增加一个真实纯文本模型用例，不要求宿主提供本身不开放的模型选择。dsh、Claude Code 在工具可用时按相同规则检查；工具缺失时标记“跳过：验证环境不可用”。看不到 Codex 实际请求时该项仍未证实，不能算作基准完整通过。素材生成和目视检查在制作阶段完成，被测会话不预先携带表情图像上下文。

每个目标客户端记录 OS、宿主形态与版本、插件/核心/协议版本、模型、输入绑定方式、显示方式、操作证据与限制。成功安装、编译或 Schema 通过只证明对应局部结果。

## Out of Scope（范围之外）

1. 传统 IM 协议适配、自动复用既有 IM 语义体系。
2. 单次发送修改表情语义，或后台自动改写已确认版本。
3. 产品内置 AI 绘图、必须依赖视觉模型的创作流程、逐次识图或专用情绪分类；开发阶段使用 imagegen 制作素材不在此排除范围。
4. Amoji 账号、自动跨设备同步、公共表情市场、自动公开个人库。
5. 声音、长视频、交互式角色和 3D 形象。
6. 以一个客户端的成功推断其全部 CLI/IDE/桌面形态支持，或承诺所有模型表达质量一致。
7. 将自建客户端、独立图库或复制粘贴文本路径包装成已完成官方宿主双向接入。
8. 第一阶段接入原型中制作完整基础库、完成全部管理界面或发布正式产品。
9. 未经范围决策直接扩大为通用 IM、用户情绪诊断或人格系统。
10. 本次 Spec 编写过程中安装插件、调用模型进行原型验证或自动公开发布软件。
