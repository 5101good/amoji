# Marketplace operations and recovery

[中文](marketplace-operations.md)

The public origin is https://amoji.ai-web.ai. The operator owns human review, report handling and recovery drills. The service targets global users; regional reachability depends on measured networks. Authentication sends neither verification nor password-recovery emails. Browsing is anonymous; submission requires an account and reviewers cannot approve their own work. Public service availability and plugin distribution are separate evidence, without implying a host marketplace listing.

## Deployment and rollback

Use Node.js 24, locked dependencies and the production environment in `apps/marketplace/wrangler.jsonc`. Deploy additive D1 migrations, then API/assets, then clients. Never rerun applied DDL or recreate/rename the existing `free-runtime-v1` SQLite DO migration. Bind only `amoji.ai-web.ai`; preserve the root domain and unrelated services. R2 CORS permits only the formal origin. Uploads default to disabled until account usage, credentials and acceptance are checked.

Preserve existing `BETTER_AUTH_SECRET`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` when deploying. D1 Read can retrieve database information, but the live D1 export request returns 401 with that permission; automatic backups require D1 Write on `D1_BACKUP_API_TOKEN`. This grants account-wide D1 read/write management and cannot be scoped to one database or export alone, so obtain explicit operator approval before enabling it. The application only reads database information and exports SQL; it does not write or delete databases. R2 writes use the private binding without granting R2 permissions to this token. Keep secrets out of source, artifacts and logs. Verify a successful backup after rotation. An authorized operator can instead export manually, store the snapshot in R2 and verify it; a manual drill does not establish successful automatic backups.

Record Worker version/deployment, D1 migrations, routes and client digest. Roll back to the previous Worker version and recheck catalog, login and upload Origin. Keep additive compatible schema. Local DB5 downgrades require stopping every host/shared writer, exporting new data and restoring the consistent pre-upgrade backup. Never open DB5 using an old binary or edit user_version.

## Official collection ordering

The public directory, homepage SSR, search and pagination share this order: Classic, Office, other official Amoji collections, then community collections. Each group is ordered by newest publication first. Official status depends only on the operator-maintained `market_official_creator.account_id`, never an editable name, author credit or source URL. Official collections still require independent review.

After applying `0009-official-catalog.sql`, verify the creator account ID and register it in `market_official_creator` with a reason and timestamp. Future approved publications from that account automatically receive priority `1`. Backfill existing collections only after checking ownership through `market_upload_pack.owner`: set `market_public_pack.priority` to `3` for Classic, `2` for Office, `1` for other official collections and `0` for community collections. New releases of an existing collection preserve its pin. When revoking an official designation, also reset priorities on its existing collections; never identify collections by name alone.

Catalog cursors include priority, update time and pack ID; clients must treat them as opaque. Cursors created before this ordering change require a refresh from the first page. Unpublished releases disappear from discovery and stop serving public downloads while retaining history and audit records.

## Quotas and diagnostics

Do not enable Workers Paid, Containers or automatic upgrades. Daily check actual Workers/D1/R2/SQLite DO shared usage, failures and storage. Application limits do not prove remaining account allowance. Stop new uploads before investigating exhaustion.

Daily application limits include 128 reservations/validations, 256 signatures, 2000 password computations, at most 100 unreclaimed uploads and 1 GiB reserved storage. Public reads allow 120/minute/IP; reports allow 5/hour. Signed-URL replay may consume additional R2 operations, so these limits are not an absolute billing cap. Set `UPLOAD_ENABLED=false` near account thresholds and verify rejection while published reads/reporting remain available. Retain error codes/request IDs, never cookies, credentials, full headers, SQL or model inputs.

`GET /v1/health` shares the persistent 120/minute/IP catalog limit and exposes backup state and the latest successful snapshot time; missing, failed or older-than-24-hour snapshots return 503. Monitor non-200 responses. The timestamp conservatively uses export start rather than delayed completion. API `Server-Timing: amoji;dur=…` includes Worker/DO service work, excluding the client network.

Private `backups/status.json` retains bounded failure codes, stages, exception kinds, export HTTP status and numeric API error codes. An export authorization failure may also record the HTTP status of an extra read-only diagnostic. Provider messages, tokens and signed URLs are excluded, and the public health endpoint does not expose these diagnostics.

## Private backup and actual recovery

The existing 15-minute cron checks backups in a separate backup DO. Start a new snapshot every 12 hours to leave retry margin. Continuously poll the official D1 export within one invocation, capped at 24 requests and 120 seconds. Do not defer active export polling until the next cron: D1 automatically cancels unattended exports. Preserve the last good snapshot after failure and start a fresh export on the next cron; bookmarks remain in memory for one attempt only. Downloads allow only the observed Cloudflare export hostname and reject redirects. SQL uses fixed-length streaming with incremental SHA-256 and is capped at 256 MiB; over-limit backups fail without replacing the previous good snapshot. SQL and state live under `backups/`, retained for at most 30 days independently of export success and business cleanup. A 2 GiB total backup budget removes oldest snapshots first while preserving the current good snapshot until its replacement is durable. Random immutable object keys bind to a SHA-256 in the status record. Expiry also removes the last successful snapshot and exposes failure. Publish the success pointer only after the complete SQL object is durable. Reevaluate capacity before exceeding the bound; never truncate.

Backups contain authentication/private content and are restricted to authorized operators, without public download. Published sealed objects retain immutable digest-bound references. Recovery must verify objects as well as SQL. Backup residues after account deletion expire within 30 days. Same-platform storage is not provider-independent disaster recovery.

To verify automatic dispatch, open Cron history from the Worker's Settings → Trigger Events → Next link and check the natural invocation time and outcome; real-time logs can also confirm the scheduled event and `/backup` invocation. Then inspect `/v1/health` and private `backups/status.json`: a successful Cron outcome only means its handler returned normally; export failures can still be recorded in backup state. If the latest successful snapshot is less than 12 hours old and has not failed, a normal invocation creates no new SQL object. Do not delete backups or alter timestamps merely to force a new file. A manual call to the backup function does not prove natural scheduling.

For a drill: privately retrieve the exact successful SQL/status into a 0700 directory with 0600 files; run `node apps/marketplace/scripts/verify-backup.mjs SQL_FILE STATUS_JSON NEW_PRIVATE_DIRECTORY` to verify digest, SQLite integrity/foreign keys and exact release/pointer state. This is offline verification only. Create isolated D1/R2/Worker resources, import the same SQL into the empty database, copy required sealed objects and verify each digest. Confirm exact review/removal state and anonymously retrieve approved content while denying private/removed releases. Record snapshot/start/completion times and prove RPO ≤24h/RTO ≤4h. Clean up only drill resources, retaining redacted evidence and formal backups. Time Travel and scripts alone do not establish a successful restore.

## Performance

The build embeds the homepage template and minified base CSS in the Worker, eliminating a separate static-asset service fetch, and adds the CSS's exact SHA-256 to CSP without `unsafe-inline`. Catalog data is still queried live, rendered on the server and reused by the client, removing a separate CSS dependency and duplicate catalog request from first paint. Browser measurements must still include connection setup and public network latency; server timing is not a substitute.

`apps/marketplace/scripts/catalog-load-fixture.mjs PRIVATE_OUTPUT.sql` generates 10000 synthetic packs for an **isolated performance database only**. Never pollute the production catalog. Apply the same migrations and Worker build with real D1 and record the count. `measure-catalog.mjs HTTPS_ORIGIN NETWORK_LABEL PRIVATE_OUTPUT.json` runs 100 reads with 20 concurrent clients, requiring server metadata p95 ≤500ms and first-page p95 ≤2s on a declared regional network. HTTP timing does not establish browser rendering; verify the actual page separately.

Human user/creator studies require informed participants and remain explicitly unverified until actually performed.

For an isolated read benchmark, start with `catalog-load-fixture.mjs OUTPUT.sql --metadata-only --start=1 --count=100` to calibrate usage, then load explicit ranges in bounded batches. This mode preserves every production catalog column, primary key, unique index and sort index; it omits foreign keys that constrain publication writes. Every package retains a complete official sample manifest. This measures catalog reads, not 10,000 real publication workflows. Read actual account-wide daily D1 usage first, inspect `rows_written` and `rows_read` after every batch, and reserve at least 20,000 writes and 1,000,000 reads for production. Stop if remaining capacity is unknown or insufficient. Separately restore the complete production SQL into an isolated cloud database; this fixture cannot replace that recovery drill.
